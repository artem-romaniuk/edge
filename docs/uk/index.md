# Edge: спільний зворотний проксі

> 🇬🇧 [This page in English](../en/index.md) · ⬆️ [README](../../README.md)

`edge` — це Docker Compose-проєкт з одним сервісом, `caddy`. Це єдине на сервері, що має
опубліковані порти, а кожен додаток за ним доступний через Docker-мережу.

---

## 1. Чому проксі — окремий проєкт

- **Порти 80 і 443 може тримати лише один процес.** Двом додаткам на одному сервері потрібні одні
  вхідні двері, і вони не можуть належати жодному з них.
- **Додатки релізяться незалежно.** Поки Caddy жив усередині `deploy/`, реліз Cloche чи
  `docker compose down` вимикали б разом із собою всі інші сайти на сервері. Тепер життєвий цикл
  додатка торкається лише його власних контейнерів.
- **Одне місце для TLS.** Сертифікати всіх доменів, їх поновлення і ACME-акаунт живуть в одному
  томі, за однією конфігурацією.

---

## 2. Структура

```caddyfile
{
	email {$ACME_EMAIL}
}

(access_log) {
	log {
		output stderr
		format json
	}
}

import sites/*.caddy
```

`Caddyfile` містить лише спільне: адресу ACME-акаунта, сніпет `(access_log)` (один JSON-рядок на
запит у stderr для кожного сайту, що каже `import access_log`) та імпорт усіх файлів сайтів. Кожен
додаток має рівно один файл у `sites/`, названий його іменем, з усіма його іменами хостів і
маршрутами.

Домени беруться з оточення: `{$CLOCHE_DOMAIN}` — синтаксис змінних оточення Caddy, який
розв'язується на старті, а `docker-compose.yml` передає кожну змінну з `.env` у контейнер.
`Caddyfile` і `sites/` змонтовані лише для читання.

Що робить кожен хост Cloche і чому — `app.`, `auth.` з його h2c-переходом до Zitadel, `logs.` з
відрізаними шляхами інжесту Seq — описано разом з рештою Cloche, у
[Caddy і TLS](../../../deploy/docs/uk/04-edge/index.md).

## 3. Контракт із додатком

1. **Одна зовнішня bridge-мережа на додаток, з іменем `<app>_edge`.** Жодна сторона нею не володіє:
   `scripts/up.sh` створює кожну зовнішню мережу з `docker-compose.yml`, якої ще немає, а
   деплой-скрипт додатка робить те саме для своєї (`deploy/scripts/deploy.sh` створює
   `cloche_edge`).
2. **Додаток під'єднує лише те, що цього потребує**: сервіси, до яких проксує Caddy, і сервіси, яким
   треба звертатися до одного з публічних імен додатка через Caddy. Бази даних і внутрішні сервіси
   лишаються в приватних мережах додатка.
3. **Кожен upstream отримує унікальний мережевий аліас `<app>-<service>`** (`cloche-web`,
   `cloche-zitadel`, `cloche-zitadel-login`, `cloche-seq`), і файл сайту використовує лише їх.
   Caddy сидить у мережах кількох додатків одночасно; якщо у двох із них є сервіс `web`, голе ім'я
   розв'яжеться в той, який DNS Docker поверне першим.
4. **Додаток не публікує портів.** Caddy — єдиний вхід до нього.
5. **Додатки не бачать одне одного.** Кожна мережа `<app>_edge` з'єднує Caddy лише з одним
   додатком; у кількох мережах одночасно сидить тільки Caddy.

Під'єднання Caddy до `cloche_edge` несе аліас `auth.${CLOCHE_DOMAIN}`. Коли `api` чи `billing`
Cloche розв'язують `auth.<домен>`, щоб отримати JWKS Zitadel, вони отримують адресу контейнера
Caddy, тож виклик проходить той самий TLS і маршрутизацію, що й браузерний, але не покидає хост.
Стек не залежить від того, чи підтримує провайдер hairpin NAT. Приберіть аліас, якщо Zitadel колись
переїде на іншу машину.

### Додатки за цим проксі

| Додаток | Файл сайту | Мережа | Імена хостів | Upstream-и |
|---------|------------|--------|--------------|------------|
| Cloche | `sites/cloche.caddy` | `cloche_edge` | `{$CLOCHE_DOMAIN}`, `app.`, `auth.`, `logs.` | `cloche-web`, `cloche-zitadel`, `cloche-zitadel-login`, `cloche-seq` |
| Ledger | `sites/ledger.caddy` | `ledger_edge` | `{$LEDGER_DOMAIN}`, `app.` | `ledger-web` |

Ledger влаштований як Cloche, але без ідентичності й логів: один nginx-контейнер `web` віддає
лендинг на голому домені, а SPA з проксі `/api` — на `app.`, розрізняючи їх за `Host`. Його
compose-файл винен цьому проксі рівно те саме, що й Cloche: зовнішню мережу `ledger_edge`, яку його
деплой-скрипт створює, якщо її немає, і аліас `ledger-web` на `web` — і нічого більше: імені `auth.`
розв'язувати не треба, тож його API в `ledger_edge` не входить. Поки цей стек не запущено, Caddy
відповідає `502` на іменах Ledger; сертифікати буде видано, щойно їхні DNS-записи вкажуть сюди.

## 4. `.env`

| Змінна | | |
|--------|--|--|
| `ACME_EMAIL` | обов'язкова | Адреса акаунта Let's Encrypt: туди приходять попередження про закінчення терміну і повідомлення акаунта |
| `CLOCHE_DOMAIN` | обов'язкова | Зареєстрований домен Cloche. **Має дорівнювати `DOMAIN` у `deploy/.env`** — Cloche будує з того свої URL, CORS-origin і issuer Zitadel, а Caddy обслуговує цей |
| `LEDGER_DOMAIN` | обов'язкова | Зареєстрований домен Ledger, `ledgercloud.bid`. Має дорівнювати домену, з яким налаштовано деплой самого Ledger |

`chmod 600 .env`. Секретів у ньому поки немає, але він у gitignore, як і кожен інший `.env`.

## 5. Додавання ще одного додатка

1. **DNS.** Спрямуйте A/AAAA-записи кожного імені хоста на цей сервер ще до першого старту —
   інакше Caddy повторюватиме спроби отримати сертифікат з затримкою, доки записи не з'являться.
2. **Compose-файл додатка.** Оголосіть мережу зовнішньою і дайте кожному upstream аліас; портів не
   публікуйте:

   ```yaml
   services:
     web:
       networks:
         edge:
           aliases:
             - other-web
   networks:
     edge:
       external: true
       name: other_edge
   ```

3. **`docker-compose.yml` тут.** Додайте мережу на верхньому рівні та в `caddy`, і передайте домен:

   ```yaml
   services:
     caddy:
       environment:
         OTHER_DOMAIN: ${OTHER_DOMAIN:?set OTHER_DOMAIN in edge/.env}
       networks:
         other:
   networks:
     other:
       external: true
       name: other_edge
   ```

4. **`.env` і `.env.example`.** Додайте `OTHER_DOMAIN`.
5. **`sites/other.caddy`.**

   ```caddyfile
   {$OTHER_DOMAIN} {
   	import access_log
   	reverse_proxy other-web:80
   }
   ```

6. **`./scripts/up.sh`.** Він створить `other_edge`, якщо її немає, перестворить Caddy з новою
   мережею і перезавантажить конфігурацію.

## 6. Експлуатація

`scripts/up.sh` — це весь робочий процес: і для першого старту, і для зміни Caddyfile, і для
оновлення образу:

1. відмовляється працювати без `.env`;
2. створює кожну зовнішню мережу з `docker-compose.yml`, якої не існує;
3. `docker compose pull`, потім `docker compose up -d --remove-orphans`;
4. `caddy validate`, потім `caddy reload`.

Reload потрібен, бо `Caddyfile` і `sites/` — bind-монтування: compose не бачить зміни їхнього
вмісту, тож `up -d` не чіпає запущений Caddy. Reload підміняє конфігурацію без рестарту й без
розірваних з'єднань; конфігурація, що не пройшла валідацію, зупиняє скрипт до reload, і запущений
Caddy далі обслуговує стару. Контейнер, який `up -d` щойно (пере)створив, читає файли на старті,
тож перед оновленням образу перевірте конфігурацію.

```bash
docker compose logs -f caddy                                                     # видача, поновлення, помилки
docker compose exec caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
docker compose exec caddy caddy reload  --config /etc/caddy/Caddyfile
```

| Том | Вміст | Якщо його втратити |
|-----|-------|--------------------|
| `edge_caddy_data` | Сертифікати всіх доменів і ключ ACME-акаунта | Caddy перевидасть усе на наступному старті, але повторювана втрата впреться в ліміт Let's Encrypt — 50 сертифікатів на зареєстрований домен за тиждень |
| `edge_caddy_config` | Автозбережена конфігурація Caddy | Нешкідливо |

**Оновлення Caddy.** `caddy:2-alpine` іде за останньою 2.x; `./scripts/up.sh` стягує образ і
перестворює контейнер, якщо той змінився.

## 7. Логи

`vector` Cloche читає вивід цього Caddy з Docker-сокета, розпізнаючи його за лейблами
`com.docker.compose.project=edge` і `com.docker.compose.service=caddy`. Рядки access-логу
лишаються, лише якщо хост запиту — `DOMAIN` Cloche або один з його піддоменів, тож трафік інших
додатків ніколи не потрапляє в Seq Cloche. Решта рядків Caddy — видача сертифікатів, поновлення,
помилки — відправляються повністю, для всіх доменів. Див. [Логи](../../../deploy/docs/uk/07-operations/index.md#4-логи)
Cloche.

Власного сервера логів у Ledger немає: його запити є в access-лозі цього Caddy, їх читають через
`docker compose logs caddy` тут.

## 8. Перехід від Caddy всередині `deploy/`

Обидва Caddy хочуть 80 і 443, тож старий має зникнути до старту нового:

```bash
cd deploy && ./scripts/deploy.sh   # створює cloche_edge, прибирає осиротілий caddy
cd ../edge && ./scripts/up.sh      # спільний Caddy забирає 80 і 443
docker volume rm cloche_caddy_data cloche_caddy_config
```

Між двома командами сайти недоступні, а сертифікати видаються наново, а не переносяться —
прийнятно, поки Cloche не запущено.

## 9. Діагностика

| Симптом | Причина |
|---------|---------|
| `502 Bad Gateway` | Upstream не в мережі `<app>_edge` свого додатка, або його аліас відрізняється від того, що в `sites/<app>.caddy`. `docker network inspect cloche_edge` показує учасників і їхні аліаси |
| `network cloche_edge declared as external, but could not be found` | Мережі ще немає. Її створює `./scripts/up.sh` або деплой-скрипт додатка |
| `port is already allocated` на 80/443 | Порти тримає щось інше — зазвичай старий Caddy з `deploy/`; див. §8 |
